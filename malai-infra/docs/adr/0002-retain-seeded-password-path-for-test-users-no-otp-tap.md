# Non-prod test login: retain a seeded password path for the test user; drop the OTP code tap

Supersedes [ADR-0001](0001-non-prod-otp-code-tap-via-custom-message-lambda.md).

ADR-0001 accepted a non-prod code tap — the CustomMessage Lambda writing `{email → code}` to DynamoDB — so Playwright and the seeded demo user (Sarah, who has no real inbox) could obtain sign-in codes. Building it (issue 02) surfaced a blocking fact that invalidates the mechanism: **the CustomMessage Lambda only ever receives the `{####}` placeholder, never the plaintext code.** Cognito generates the code internally and substitutes it into the message *after* the Lambda returns; the Lambda is a renderer, not a participant in the code's lifecycle. It cannot write the real code because it never holds it, and it cannot substitute its own code (the email contract requires `{####}` or Cognito sends nothing, and Cognito validates against the code *it* generated, not one the Lambda invents).

The only Cognito-native way to capture the plaintext is the **CustomEmailSender** trigger (Cognito hands the Lambda the code KMS-encrypted; the Lambda decrypts it and must then send *all* auth email itself via SES). That is a large, security-relevant re-architecture, well beyond the tracer-bullet slice issue 02 was scoped as, and it contradicts ADR-0001's own "via the CustomMessage Lambda" decision.

Rather than take that on for a demo-scale need, we **retain a password path for the seeded test user.** Sarah is seeded into Cognito with an email/password (backend seeder, unchanged — she is *not* migrated to passwordless); real users sign in passwordless via EMAIL_OTP. Playwright and demo operators log in as Sarah with her password. EMAIL_OTP stays enabled *additively* (already shipped in issue 01); password auth is **not** removed. This revives the "keep a password path for test users" option ADR-0001 had rejected — now chosen with the new knowledge that the originally-accepted tap is not buildable on the CustomMessage trigger.

## Considered options

- **CustomEmailSender pivot** *(rejected for now).* The only Cognito-native code tap. But a large security-relevant re-architecture (new KMS key, `kms:Decrypt`, the Lambda sends every auth email via SES, bundle `@aws-crypto/client-node`), and it contradicts ADR-0001's CustomMessage mechanism. Revisit only if automated EMAIL_OTP-login testing becomes a hard requirement.
- **Code tap via the CustomMessage Lambda** *(no longer viable).* The ADR-0001 decision. Blocked: the Lambda never sees the plaintext code, only `{####}`.
- **Retain a seeded password path for the test user** *(accepted).* Zero new infra — after issue 01, EMAIL_OTP already coexists with password on the pool and the app client. Sarah logs in by password; real users by OTP.

## Consequences

- Password auth stays enabled on the pool: `sign_in_policy` keeps `PASSWORD` alongside `EMAIL_OTP`, and the app client keeps `ALLOW_USER_PASSWORD_AUTH`. The cleanup slice (issue 03 — remove password flows, wipe password-era users) is **cancelled**, not deferred.
- **The EMAIL_OTP login journey is not covered by automated tests** — there is no programmatic way to obtain a real user's code without the tap. Verify it manually. Registration and login for real users are otherwise unaffected, and the live demo still shows the genuine branded OTP email.
- No DynamoDB table, no KMS key, no Lambda IAM additions, no `@aws-crypto` dependency, no CustomEmailSender. The deployable Lambda zip stays dependency-free.
- A prospect reading the Terraform will see password auth retained alongside EMAIL_OTP. Unlike the tap, this is not a visible-by-design security exception; it is a test-affordance confined to non-prod seeded users. If the prod-shaped pitch ever needs password auth gone, that reopens the CustomEmailSender pivot.
- **`ALLOW_USER_PASSWORD_AUTH` is now load-bearing — do not remove it.** Sarah's test/CI login depends on the app client retaining this flow (and the pool retaining the `PASSWORD` first factor). The originally-planned cleanup that stripped them is cancelled (infra issue 03 → `wontfix`); a future "finish the passwordless cutover" change must not silently re-introduce that removal.
- **Advanced security (`ENFORCED`) scrutinises password sign-in.** The pool runs compromised-credentials + adaptive auth on every sign-in, and a programmatic `USER_PASSWORD_AUTH` from CI (unusual IP, headless, no device history) is exactly the shape adaptive auth flags — it may add risk friction or demand `UserContextData`. EMAIL_OTP logins already pass under `ENFORCED`, but the password path is new; verify Sarah's direct login against dev early. Fallback if it bites: `advanced_security_mode = "AUDIT"` in non-prod only, or supply context data. The token itself, once issued, is an ordinary Cognito access token — the backend `JwtDecoderFilter` validates only signature/issuer/expiry/`token_use`/`cognito:groups`, none of which encode the auth flow, so it cannot distinguish a password-flow token from an EMAIL_OTP one.
- **No live UI gesture to sign in as Sarah.** This solves *automated* login (Playwright drives `InitiateAuth` + cookie injection). A human demo operator has no on-screen way to log in as Sarah — the webapp UI is OTP-only and Sarah has no inbox. For a live pitch, demo the OTP flow with a real-inbox account and use Sarah for pre-seeded state; if "present live as Sarah" is ever required, it needs its own decision (e.g. a non-prod-only affordance).
- Cross-repo: the backend seeder must keep seeding Sarah with a password (do not migrate her to passwordless); the webapp Playwright `auth.setup` logs in as Sarah by password rather than polling a tap. Both are tracked in their own repos' PRDs.
