# 04 — ENFORCE parks: flagged payments land REFERRED

Status: done
Category: enhancement

## What to build

From `.scratch/payment-screening/PRD.md`. The first half of enforcement: in `ENFORCE` mode, a flagging verdict parks the payment in the new `REFERRED` Lifecycle state instead of dispatching — ledger Hold intact, no scheme traffic, decision id stored on the payment row as an opaque pointer. `SHADOW` behaviour is untouched. This slice also lays the full lifecycle and contract groundwork the resolver (issue 06) enacts against:

- One migration: the payments table admits `REFERRED` and `DECLINED` and gains a nullable decision-id column
- The public contract's payment-state enum gains `REFERRED` and `DECLINED` — a deliberate, coordinated widening (the compatibility check will flag response-enum widening; approve it consciously). No customer-facing decline reason, per the anti-tipping-off decision
- A `PAYMENT_REFERRED` audit event joins the payment lifecycle family
- Invariants hold: a `REFERRED` payment has exactly one active Hold and no ledger entries

`DECLINED` exists in schema and contract from this slice but nothing transitions into it yet — that is issue 06.

### Resolution (2026-07-20)

Enforcement's first half landed: in `ENFORCE` mode a flagging **Verdict** parks the payment
in `REFERRED` before it reaches the rail, with the ledger **Hold** intact and the **Model
Decision**'s id pinned on the row. `SHADOW` is byte-for-byte unchanged.

**Key decisions**

- **A referred payment is born `REFERRED`.** Initiation resolves the state before it returns,
  rather than saving `PENDING` and transitioning afterwards, so a customer never observes a
  `PENDING` window on a payment that was never dispatched. Mechanically the row is saved
  `PENDING` and updated inside the same `@Transactional` initiation — the two writes are one
  atomic act, and the DB only ever exposes `REFERRED`.
- **Ordering obeys the issue-03 audit-chain invariant.** The screening call still runs after
  `paymentRepository.save(...)` and *before* `auditWriter.record(PAYMENT_INITIATED)`; the new
  `PAYMENT_REFERRED` event is recorded after it, not before. Recording it before the screening
  write would have reintroduced the self-deadlock issue 03 diagnosed (the MDR's own decision
  write audits on the same `global` chain scope, so a loopback call made after the chain lock
  is taken blocks until the caller's read timeout). Acceptance tests are blind to this by
  construction — the ordering is a rule, not something a green suite proves.
- **`PAYMENT_INITIATED` still fires, and carries the final state.** The referral joins the
  lifecycle family rather than replacing its head: a referred payment audits
  `PAYMENT_INITIATED` (afterState `state = REFERRED`) then `PAYMENT_REFERRED`. The referral
  event is recorded as `SYSTEM` against the account holder, matching `PAYMENT_SETTLED` /
  `PAYMENT_RETURNED` — the bank referred the payment, the customer did not.
- **The decision id is an opaque pointer.** `payments.screening_decision_id` is a plain
  nullable `UUID` with no foreign key into the MDR's tables, per ADR-0009. The audit event
  carries it too, which is what makes the ops linkage walkable from the chain alone.
- **The migration adds only a column.** `payments.state` is a `VARCHAR(15)` with no `CHECK`
  constraint (V15), so `REFERRED` and `DECLINED` need no DDL to be admitted — V26 says so
  explicitly so a reader doesn't go looking for the constraint that would have needed widening.
- **Mode is flipped per-test by mutating the bound properties bean** (`ScreeningProperties.mode`
  is now a `var`, set via a new `screeningModeIs(...)` given-step). The Spring context is a
  per-JVM singleton, so a second context per mode was not an option; `PaymentsAcceptanceTest`
  resets the mode to `SHADOW` in a `@BeforeEach`, mirroring `stubbedTimeService().reset()`, so
  an enforce test can never leak into the ~40 other payments tests.
- **`DECLINED` is schema + contract only.** Nothing transitions into it — that is issue 06.

**Contract compatibility check (recorded consciously, as the issue asks)**

`oasdiff breaking` (via `docker run --rm tufin/oasdiff`) against `HEAD`'s spec:

```
4 changes: 0 error, 4 warning, 0 info
warning [response-property-enum-value-added] POST /api/v1/payments  → REFERRED, DECLINED (201)
warning [response-property-enum-value-added] GET  /api/v1/payments/{paymentId} → REFERRED, DECLINED (200)
```

Exit 0 — warnings, not errors, because `PaymentState` appears only in responses (never in a
request body, so there is no enum narrowing anywhere). The warning is the correct signal and is
accepted deliberately: the webapp must learn to render two new states. `x-extensible-enum`
(oasdiff's suggested remedy) is not adopted — the generated TypeScript client's exhaustive
union is exactly the compile-time nudge we want on the webapp side.
