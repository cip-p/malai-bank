# 06 — Resolver enacts rulings: REFERRED payments release or decline

Status: done
Category: enhancement

## What to build

From `.scratch/payment-screening/PRD.md`, per ADR-0008 and ADR-0009. The enforcement loop closes: a resolver in payments sweeps `REFERRED` payments on a ~5-second property-tunable cadence, consults the internal gate via the client for each stored decision id, and enacts the actionable verdict:

- Actionable verdict `DECLINE` (an accept ruling on the model's flag, or an edit that upholds it) → `REFERRED → DECLINED`: Hold released, nothing posted, no scheme traffic, `PAYMENT_DECLINED` audited
- Actionable verdict `APPROVE` (typically an edit overriding the model) → `REFERRED → PENDING`: `PAYMENT_RELEASED` audited, the payment dispatches to its rail and rides the normal settle/return path
- Gate conflict (no ruling, or ruling in force is reject) → stays `REFERRED`, by design
- Unparseable actionable output → conservatively stays `REFERRED`

Transitions fire only from `REFERRED`, so re-polls and retried enactments are naturally idempotent. The poller is vacuous in `SHADOW` mode (nothing is ever `REFERRED`) and needs no mode gating. Any new custom repository finder gets its own test per the house rule.

## Acceptance criteria

- [x] Accept-the-DECLINE: the payment lands `DECLINED` with Hold released, no ledger entries, `PAYMENT_DECLINED` audited — full-entity DB assertions
- [x] Edit-to-APPROVE: the payment moves to `PENDING`, dispatches, and settles through the existing rail machinery; `PAYMENT_RELEASED` audited
- [x] Reject ruling and no-ruling both leave the payment `REFERRED`; a later disposition re-governs it (latest-wins re-rule enacted on a subsequent sweep)
- [x] Unparseable actionable output leaves the payment `REFERRED`
- [x] A second sweep over an already-enacted payment changes nothing (idempotency pinned)
- [x] The cadence is property-tunable; acceptance tests drive the sweep deterministically rather than sleeping
- [x] Repository finder(s) for referred payments tested
- [x] `mvn install` green

### Resolution (2026-07-20)

The enforcement loop closes. `ReferredPaymentResolver` sweeps every **Payment** parked in
**Referral**, presents its pinned **Model Decision** id to the MDR's **Gate**, and enacts the
Actionable output: `DECLINE` declines and releases the **Hold**, `APPROVE` releases the payment
to `PENDING` and dispatches it to its **Rail**. Everything else leaves the payment parked.

**Key decisions**

- **A third scheduler in the house shape, not a new one.** `ReferredPaymentResolver` is a
  deliberate structural clone of `StandingOrderExecutor` and `DirectDebitCollectionRequester`:
  ShedLock-coordinated `runOnSchedule()` delegating to a public sweep method, a per-item
  `try`/`catch` that logs and skips so one bad payment can't stall the batch, a `LOCK_NAME`
  companion constant, and a class-level KDoc. That shape is what the ArchUnit rule enforcing
  `@SchedulerLock` expects, and it is what makes the cadence testable — like both siblings, the
  cron is `-` in test properties and acceptance tests call `resolveReferredPayments()` directly,
  so nothing sleeps.
- **The resolver decides; `PaymentLifecycleService` transitions.** The new
  `transitionToDeclined` / `transitionToReleased` sit beside the existing `transitionToSettled` /
  `transitionToReturned`, so every **Lifecycle** state change in payments still happens in one
  class. The resolver holds no transaction and writes no state.
- **The gate call happens outside the enacting transaction** — the audit-chain invariant issue 03
  paid for. `transitionToDeclined` / `transitionToReleased` each audit, which locks the single
  global `chain_head` row for the rest of their transaction; a loopback call to the MDR made while
  that lock is held deadlocks against the MDR's own audit write. So the resolver reads the gate
  first, then calls a `@Transactional` method that makes no out-of-JVM call before its audit.
  Acceptance tests cannot see this (the MDR is a WireMock stub) — the invariant is written down in
  `payments-service/CONTEXT.md` and issue 07's e2e is the guard.
- **Idempotency is the state guard, not a dedup table.** Each transition re-reads the payment
  inside its own transaction and returns unless it is *still* `REFERRED`. A duplicate sweep, a
  re-poll and a retried enactment are therefore all no-ops for free. Pinned by a test that sweeps
  twice and asserts exactly one gate call, one hold release and one `PAYMENT_DECLINED`.
- **Branch on the parsed actionable output's `decision`, never on the ruling kind** — following
  issue 05's note. An `EDIT` can uphold a `DECLINE` exactly as an `ACCEPT` can, so `ruling` is the
  wrong seam; it is logged, never switched on.
- **Everything that is not an actionable `APPROVE` or `DECLINE` leaves the payment parked**, and
  that is ADR-0008's conservative-only invariant holding rather than a failure: a refused gate
  (`null` — no ruling yet, or a reject in force), output that isn't JSON, a verdict outside the
  `ScreeningDecision` enum, and a gate outage all fall through to "still `REFERRED`, try next
  sweep". Because the payment stays `REFERRED`, latest-ruling-wins re-governance is automatic —
  a later disposition is picked up by the next sweep, pinned by a test.
- **`fx_target_currency` closes a gap the referral path opened** — the one genuinely new finding
  of this slice. A SWIFT payment's row stores the *source* currency in `currency` (V15 semantics,
  unchanged); the requested *target* currency lived only in the initiation request, which is long
  gone by the time the resolver dispatches a released payment. Without persisting it, a
  referred-then-released international payment would have reached the scheme with no FX leg at
  all — a silent wrong-currency dispatch that no existing test covered. V27 adds the column, the
  release path rebuilds the conversion from the stub rate table, and a dedicated acceptance test
  pins that a released SWIFT payment reaches the scheme with the same target currency an
  unreferred one carries.
- **V27's index is partial** — `(created_at) WHERE state = 'REFERRED'`. The sweep runs every five
  seconds and `REFERRED` is by a wide margin the rarest state, so indexing the others would be
  dead weight.
- **Issue 05's ERROR drip is fixed at the seam it suggested.** `AbstractMalaiClient.makeRequest`
  gained a `toleratedStatusCodes` parameter defaulting to the empty set — every existing client is
  byte-for-byte unaffected — and `MdrClient.actionableOutput` passes `409` so a gate refusal logs
  at DEBUG instead of ERROR. Without this, every five-second poll of a payment awaiting a ruling
  would have emitted an ERROR line, and a parked payment is precisely the state the demo lingers
  in. Verified: `MdrClientTest` now logs ERROR only for genuine 500s.
- **The repository finder gets its own test** per the house rule: `findByStateOrderByCreatedAtAsc`
  is pinned for filtering to the one state, ordering oldest-parked-first, and returning empty.

**Contract compatibility**

`openapi.yaml` is untouched — `git diff` over the spec is 0 lines. `REFERRED` and `DECLINED` were
already published by issue 04, and the resolver adds no route and no field: it only moves payments
between states the contract already describes.

**Notes for the next iteration (issue 07)**

- **The infra hand-off needs two env vars, not one.** `MAL_PAYMENTS_SCREENING_MODE=ENFORCE` (from
  issue 04) *and* `MAL_PAYMENTS_SCREENING_RESOLVER_CRON`, which defaults to `*/5 * * * * *` and so
  needs setting only if the demo wants a different cadence. Both belong in
  `docker-compose.e2e.yml`'s `malai-api` environment block and on the demo task definition.
  Note the default is live in production config — an unset cron means the resolver *runs*, which
  is the intent, but it also means a mis-set `MAL_PAYMENTS_SCREENING_MODE` is the only thing
  standing between the demo and enforcement.
- **e2e cannot call the bean.** Acceptance tests drive the sweep directly; e2e talks to a running
  stack over HTTP, so it must poll for the state change on the real five-second cadence. Budget
  for that in the test's wait, and prefer polling the payment's state over a fixed sleep.
- **The FX rate is re-derived at release time** from the static stub rate table, so it reproduces
  exactly today. If rates ever become time-varying, a referred-then-released payment would convert
  at release-time rather than initiation-time rate — a real product question, not a bug now.
- `PAYMENT_DECLINED` and `PAYMENT_RELEASED` follow issue 04's `PAYMENT_REFERRED` precedent:
  `SYSTEM` actor, recorded *after* the gate call, carrying the decision id in `afterState` so the
  whole story is walkable from the chain alone.
- Issue 05 predicted a 404 unknown-decision stub would be wanted. It still isn't — nothing
  exercises it, since payments only ever holds a decision id the MDR minted.
