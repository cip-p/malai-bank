### Resolution (2026-07-20)

The tracer bullet works end-to-end — but only after this slice found and fixed a defect in
issue 02 that no acceptance test could have seen.

**The defect: shadow screening deadlocked every screened payment against the audit chain.**
On the first run of the new e2e test the payment hung for 180s and then 500'd. Sampling
`pg_stat_activity` during the hang was conclusive: the MDR write was blocked on
`SELECT last_hash, last_seq FROM chain_head WHERE scope = ? FOR UPDATE` (wait event
`Lock/transactionid`) while the payments connection sat `idle in transaction` having just run
`UPDATE chain_head SET last_hash = ?, last_seq = ? WHERE scope = ?`.

The cause is structural, not incidental. `MdrDecisionService.recordDecision` records an
`MDR_DECISION_RECORDED` audit event on the **`global`** chain scope — deliberate double-entry
per ADR-0007. `PaymentsService.initiate` had already recorded `PAYMENT_INITIATED` on that same
scope, so its open transaction held the one global `chain_head` row. In the bundled `malai-api`
topology the screening call loops straight back into the same JVM and the same Postgres, so the
MDR's handler waited on a lock the caller would not release until it returned — a genuine
self-deadlock, broken only when the client's 180s read timeout aborted the payments request.

Acceptance tests are blind to this by construction: there the MDR is a WireMock stub with no
database behind it, so the loopback never touches `chain_head`. The e2e slice is the only place
this is reachable. Worth noting the secondary symptom too: `SocketTimeoutException` is a
*checked* exception, so Spring's default rollback rules did **not** fire — the failed payment
committed its row. Fixing the deadlock removes the path that exposed that.

**The fix: screen before auditing.** `PaymentsService.initiate` now runs the screening call
immediately after `paymentRepository.save(...)` and *before* `auditWriter.record(PAYMENT_INITIATED)`.
That restores the ordering the rest of the method already obeyed — the account lookup and the
ledger Hold are both loopback calls made before the audit write — and states it as a rule:
**every out-of-JVM call a payment-initiating transaction makes happens before that transaction
touches the audit chain.** Recorded as an invariant in `payments-service/CONTEXT.md` so issues
04 and 06 don't reintroduce it. Nothing else moved: screening is still pre-dispatch, still inside
the transaction, so fail-open (decider) and fail-closed (MDR write) semantics are unchanged.

Consequence on the audit chain: for a screened payment, `MDR_DECISION_RECORDED` now precedes
`PAYMENT_INITIATED`. That is the honest order of events — the decision genuinely is recorded
first — and it is what the deadlock-free ordering requires.

**The e2e test.** `PaymentScreeningTest` registers a customer, seeds a balance, and pays the
watchlist counterparty (Carol Singh, 30-00-03 / 11223344 — a Lloyds entry in the stub's
fictional directory, so the payment also settles cross-bank). Watchlist rather than threshold
because it is the demo-meaningful path and issue 07 will drive the same fixture. It then asserts,
in one journey:

- the payment lands `PENDING` and reaches `SETTLED` (shadow mode does not park it)
- the admin worklist lists exactly one Decision at seq 1, `COMPLETED`, model
  `malai-screening-rules` v`1`, correlation `PAYMENT` / the real payment id, `dispositionCount`
  0 and no `rulingInForce` — i.e. awaiting ruling
- the replay read returns the recorded prompt, both context refs (`ACCOUNT` at the payer's real
  account id, `WATCHLIST` at version `2026-07-01`) with content hashes, the exact raw output
  `{"decision":"DECLINE","riskScore":25,"reasons":["WATCHLIST_COUNTERPARTY"]}`, and the matching
  verdict
- the rendered prompt names the live payment, the live payer account, and masks both account
  numbers to their last four — with `shouldNotContain` on each full account number, so the
  masking claim is proven on live data rather than fixture data
- chain verification returns `OK` over 1 row, and the `mdr_entries` row is a `MODEL_DECISION`
  with no parent
- the `PaymentsService -> MdrService` POST is on the Kensa diagram

Hash values are asserted as present (`something`) rather than pinned — the exact digests are
already pinned by `PaymentScreeningPromptTest`, and duplicating them here would make the e2e
break on every template edit for no extra coverage.
