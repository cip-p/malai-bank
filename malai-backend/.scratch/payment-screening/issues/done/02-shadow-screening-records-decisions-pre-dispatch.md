# 02 — Shadow screening: outbound payments record a Model Decision pre-dispatch

Status: done
Category: enhancement

## What to build

The tracer bullet of `.scratch/payment-screening/PRD.md`. Every customer-initiated outbound non-book Payment (FPS and SWIFT; book transfers, inbound, and scheduled executions excluded) is screened synchronously during initiation — after the ledger Hold and persistence, before rail dispatch — and the Model Decision is recorded in the MDR before the flow branches. In this slice the record is the whole effect: `SHADOW` is the only implemented mode of the new screening-mode property (default `SHADOW`; the property exists now, `ENFORCE` lands in issue 04).

The decider is a seam owned by the payments flow with one production implementation: the honest deterministic rules decider, recorded as `malai-screening-rules` version `1`. Rules: amount ≥ £10,000 flags DECLINE; one watchlist counterparty from the stub's fictional directory flags DECLINE at any amount; one armed exact amount simulates a decider timeout; riskScore derives deterministically from amount band + watchlist hit. The Rendered prompt comes from a real, versioned `payment-screening/v1` Prompt template with a genuine content hash, assembling the payment's facts and a payer-account snapshot without balances. Retrieved-context refs: `ACCOUNT` (hash over the lookup actually used) and `WATCHLIST` (version + content hash). Correlation ref: `PAYMENT` / the payment id.

Failure semantics per the PRD: decider timeout/error → `TIMED_OUT`/`ERRORED` Entry appended and the payment proceeds (fail-open); MDR write failure → the payment request fails (fail-closed; Hold cleanup follows the existing dispatch-failure behaviour — verify what that is during implementation). Entry ids minted inline via the platform UUID generator.

Configuration blast radius: the MDR client's base-url property must be declared in payments-service and the aggregator app (main, test, and acceptance-boot configuration) — the known new-client gotcha. Payments acceptance diagrams gain an MdrService WireMock lane, and the new UUID mint shifts the shared test-UUID queue, so existing full-entity assertions will need updating.

## Acceptance criteria

### Resolution (2026-07-20)

Shadow screening is live: every customer-initiated outbound FPS/SWIFT payment is screened
inside initiation and its Model Decision is recorded in the MDR before the flow branches.

**The seam and its one implementation.** `ScreeningDecider` (payments-owned) declares
`modelId`/`modelVersion` and `decide(subject, renderedPrompt)`; the sole production impl is
`RulesScreeningDecider`, recorded honestly as `malai-screening-rules` version `1`. Threshold
`>= 1_000_000` minor units flags DECLINE; the watchlist counterparty flags DECLINE at any
amount; the armed amount `314_159` (pi, deliberately memorable and collision-free) throws
`ScreeningTimedOutException`. riskScore bands 10/25/45/80 by amount, +15 (capped 99) on a
watchlist hit. Reasons are `AMOUNT_AT_OR_ABOVE_THRESHOLD` / `WATCHLIST_COUNTERPARTY`.

**Watchlist counterparty: Carol Singh** (30-00-03 / 11223344, Lloyds) — chosen from the stub's
fictional directory because it is the only SETTLES entry unclaimed by seeded payees, direct
debits, standing orders, or the existing outbound acceptance fixtures. Matching is on
beneficiary name (case- and space-insensitive), so it works for SWIFT as well as FPS.

**Prompt and hashes are genuine.** `payment-screening/v1` lives at
`src/main/resources/screening/payment-screening-v1.txt`; `promptTemplateHash` is SHA-256 over
the file's actual bytes, computed at startup. `ACCOUNT` context ref hashes the canonical
projection of the account lookup actually used; `WATCHLIST` ref carries version as id and
SHA-256 over version + sorted names, so changing either changes the hash. Beneficiary and
payer identifiers are masked to the last four digits in the rendered prompt.

**Failure semantics.** Decider timeout/error -> `TIMED_OUT`/`ERRORED` entry, payment proceeds.
MDR write failure -> `MalaiClientResponseException` propagates, the request 500s, the
`@Transactional` initiation rolls the payment row back. Hold cleanup: verified that the
existing dispatch-failure behaviour leaves the ledger Hold in place (nothing compensates a
`fpsScheme.submit` throw either), so fail-closed matches the incumbent behaviour exactly --
no new product decision taken.

**Design note.** `PaymentScreener.screen(subject, serviceToken)` takes the service token as an
argument rather than injecting `PaymentsServiceTokenClient`, matching how every other client
call in payments reads (`ledgerClient.placeHold(tokenClient.getToken(), ...)`) and keeping the
screener testable without a token-client double.

**Testing.** Direct deterministic tests for the decider (11), the prompt/hashes (7), and the
screener seam (5 -- including the ERRORED branch, unreachable from the HTTP surface with a
rules decider, and the SHADOW default). Six shadow acceptance tests (FPS below threshold with
the full MDR request body pinned, SWIFT, book transfer unscreened, threshold, watchlist,
armed timeout) plus a sad-path MDR-outage test. The mode property has no reader in this slice
-- recording is structurally unconditional; issue 04 adds the branch.

**UUID queue shift.** Screening mints decisionId then entryId, so the initiation order is now
paymentId, endToEndId, [book-transfer txn], audit event id, decisionId, entryId. Existing
outbound tests only seed the first two, so none needed re-seeding -- but all 15 customer FPS/
SWIFT acceptance tests gained `and(recordModelDecisionReturns(aRecordModelDecisionResponse()))`
because an unstubbed MDR is now an unmatched WireMock request.

**Files.** payments-service: `screening/` (ScreeningProperties, ScreeningModels,
ScreeningDecider, RulesScreeningDecider, ScreeningWatchlist, PaymentScreeningPrompt,
PaymentScreener, ScreeningHashing) + the v1 template resource; `PaymentsService` wired;
pom gains the mdr client pair. Config: `malai.mdr.base-url` and
`malai.payments.screening.mode` in payments-service main/test + malai-api main/test,
`--malai.mdr.base-url` in the acceptance boot helper. Tests: `PaymentsAcceptanceTest` gains
the `WithMdrApi` lane and an `MdrService` party; new happy/sad `ScreeningPaymentsControllerTest`.
Docs: payments-service `CONTEXT.md` gains Decider, Watchlist, Screening mode.

**For issue 04/07.** The env var for the demo environment is `MAL_PAYMENTS_SCREENING_MODE`
(property `malai.payments.screening.mode`, values `SHADOW` | `ENFORCE`, default `SHADOW`).
`ScreeningResult.flagged` is the branch point enforcement will read.
