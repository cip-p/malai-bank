# 05 — Internal actionable-output gate

Status: done
Category: enhancement

## What to build

From `.scratch/payment-screening/PRD.md`, per ADR-0009. The MDR gains an internal, service-JWT-scoped actionable-output read — a thin second door onto the existing gate logic, so the ruling-in-force translation stays in exactly one place. Same semantics as the admin gate: accept serves the raw output, edit serves the stored edited output, reject or no ruling is the domain-coded conflict, unknown decision is not-found. Internal routes stay out of the public contract per the documented convention.

The MDR client (issue 01's module) gains the matching read call, with WireMock-backed tests and test-support stubs, so consumers can consult the gate without touching admin auth.

### Resolution (2026-07-20)

The **Gate** gained its second door. `GET /api/v1/internal/mdr/decisions/{decisionId}/actionable-output`
serves the same **Actionable output** the admin gate serves, to a service-JWT caller, and the
MDR client can now read it — so issue 06's resolver has something to consult.

**Key decisions**

- **A second door, not a second implementation.** The internal route delegates to the very same
  `MdrReadService.actionableOutput`, so the *accept serves raw / edit serves edited / reject and
  no-ruling refuse* translation exists in exactly one place, as ADR-0009 requires. Nothing in
  `MdrReadService` changed — the whole production delta on the service side is a controller
  method and a constructor argument. The two doors' acceptance suites are deliberately parallel
  in shape so a future divergence shows up as a diff between two files.
- **The internal route lives on the existing `InternalMdrDecisionsController`**, beside the
  write, rather than in a controller of its own: both routes are the same `/internal/mdr/decisions`
  family, and the admin side already keeps its three reads together in one class.
- **The scope is the shared `malai-internal/onboarding.write`, deliberately, not a new read
  scope.** `SecurityConfig.internalServicesFilterChain` admits exactly that one scope on every
  path matching `/api/v\d+/internal/.*`, so a narrower `…/mdr.read` would be a Cognito
  resource-server change in malai-infra plus a filter-chain change — infrastructure work, not
  controller work, and not something to smuggle into this slice. The rationale is stated on the
  controller so the next reader doesn't take the write-scope-on-a-read as an oversight.
- **A gate refusal is `null`, not an exception, at the client boundary.** `MdrClient.actionableOutput`
  returns `ActionableOutputResponse?` and maps 409 → `null`; every other non-200 still throws.
  A refusal is the gate working, not failing — "no ruling in force yet" is the *normal* state of a
  parked payment, and forcing the resolver to catch an exception for it would make the ordinary
  path the exceptional one. This follows the existing `AccountLookupClient.resolveBySortCodeAndAccountNumber`
  precedent (404 → `null`), so it is the house pattern for an expected non-2xx, not a new one.
  404 (unknown decision) deliberately still throws: payments only ever holds a decision id the
  MDR minted, so an unknown one is a real defect and should be loud.
- **A user JWT on the internal gate is 401, not 403.** The internal filter chain matches on path
  and only accepts service tokens, so an admin's user JWT never reaches `@PreAuthorize`. Pinned as
  a test because "the admin can also reach the internal door" would be a plausible-looking bug.
- **One test asserts the gate appends nothing to the chain** (`last_seq` unmoved across a read).
  The MDR is append-only, and a read that silently chained an entry would corrupt exactly the
  property the whole context exists to provide.

**Contract compatibility check**

`openapi.yaml` is untouched — internal routes stay out of the public contract per the convention
the spec itself states (its `/api/v1/internal/**` note). Verified rather than assumed:
`docker run --rm tufin/oasdiff breaking` against `HEAD`'s spec → `No changes detected`, exit 0.

**Notes for the next iteration**

- **The 409 path logs at ERROR.** `AbstractMalaiClient.makeRequest` logs `received unexpected
  status code: 409` before throwing, and the client swallows the throw — so every gate poll on a
  still-unruled payment emits an ERROR line. Issue 06 polls every ~5s per `REFERRED` payment, and
  a payment parked awaiting a ruling is precisely the state the demo lingers in, so this becomes a
  steady ERROR drip in the demo box's logs at the most-watched moment. Not fixed here: the log
  lives in shared client infrastructure used by every client, so quieting it is a cross-cutting
  change that belongs with the caller that creates the volume. Issue 06 should either add an
  "expected status codes" seam to `AbstractMalaiClient` or have the resolver back off.
- The test-support stubs are `actionableOutputReturns` / `actionableOutputIsRefused` /
  `actionableOutputFailsWithServerError`. The refusal stub is named for the 409, not for "no
  ruling", because the client genuinely cannot tell the two refusal causes apart — a `REJECT` *is*
  a Ruling in force, it just isn't an actionable one. Issue 06 will likely also want an
  unknown-decision (404) stub — deliberately not added here, since nothing tests it yet.
- The client returns the ruling (`ACCEPT` / `EDIT`) alongside the output. Issue 06 enacts on the
  *parsed actionable output*, not on the ruling kind — an `EDIT` can uphold a `DECLINE` just as an
  `ACCEPT` can, so branching on `ruling` would be the wrong seam.
