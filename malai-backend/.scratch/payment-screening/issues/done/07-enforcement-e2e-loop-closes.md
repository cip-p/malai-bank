### Infra hand-off — the demo task definition (named human follow-up, not agent-completable)

Two environment variables on the `malai-api` container in the demo environment's ECS task
definition in `malai-infra`. Same names the e2e compose file now uses, so the demo box and the
e2e stack are configured identically.

| Env var | Value | Required? | Backing property |
|---|---|---|---|
| `MAL_PAYMENTS_SCREENING_MODE` | `ENFORCE` | **Yes** | `malai.payments.screening.mode` (defaults to `SHADOW`) |
| `MAL_PAYMENTS_SCREENING_RESOLVER_CRON` | `*/5 * * * * *` | No | `malai.payments.screening.resolver.cron` (same default) |

Both are read in `malai-api/src/main/resources/application.properties`.

`MAL_PAYMENTS_SCREENING_MODE` is the whole hand-off. Unset, the demo runs in `SHADOW`: every
flagging payment is still recorded as a Model Decision and still shows in the admin worklist, but
nothing parks and nothing waits for a ruling — the referral half of the demo silently does not
happen, and it looks like a working system rather than a misconfigured one. That is the failure
mode to watch for.

`MAL_PAYMENTS_SCREENING_RESOLVER_CRON` needs setting only to change the cadence. Note the default
is live in production config: an *unset* cron means `ReferredPaymentResolver` **runs** every five
seconds, which is the intent. It is vacuous in `SHADOW` (nothing is ever `REFERRED`), so the mode
variable alone is what stands between the demo and enforcement.

Apply per the usual infra discipline, next time the environment is up (dev runtime was torn down
2026-07-19). Mirrors the coordination-record pattern of the three-surfaces credential work.
