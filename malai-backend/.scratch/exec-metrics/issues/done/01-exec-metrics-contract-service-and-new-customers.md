# 01 — The exec metrics contract, `exec-service`, and the first real number

Status: ready-for-agent
Category: enhancement

## What to build

Tracer bullet for `.scratch/exec-metrics/PRD.md`. The Exec surface gets its composed read: `GET /api/v1/exec/metrics` returns the bank's headline **Metric**s for the current **Banking day**, and the first of them — **New customers** — is real.

The contract lands whole in this slice: `bankingDay`, `asOf`, and all four metrics, each either `AVAILABLE` with its value or `UNAVAILABLE` with none. Only New customers is implemented here; deposits, cards issued, and payments stopped return `UNAVAILABLE` honestly until issues 02–04 fill them in. That is deliberate — it exercises the availability mechanism from the first slice, and each later metric becomes a one-tile flip rather than a contract change. Money metrics carry an explicit currency (see the shape below) even though the first implemented metric has none.

A new `exec-service` module owns the composition and the domain language but no tables (ADR-0011). It fans out over the existing client pairs to a service-JWT-scoped internal metric read on each owning context; `account-holder-service` gains the first of those, counting **AccountHolder**s created during the Banking day. Each fan-out leg carries its own timeout: a slow or unreachable source degrades that one metric to `UNAVAILABLE` and never delays or fails the response. All reads, so nothing here writes to the audit chain and the loopback-audit deadlock does not apply.

Gated `hasRole('ADMIN')` in this slice; issue 05 widens it to `hasAnyRole('MANAGER','ADMIN')`.

The response shape, which encodes the availability decision more precisely than prose:

```json
{
  "bankingDay": "2026-07-20",
  "asOf": "2026-07-20T14:03:11Z",
  "newCustomers":    { "status": "AVAILABLE",   "count": 12 },
  "deposits":        { "status": "UNAVAILABLE" },
  "cardsIssued":     { "status": "UNAVAILABLE" },
  "paymentsStopped": { "status": "AVAILABLE",   "amountMinorUnits": 1000000, "currency": "GBP" }
}
```

`UNAVAILABLE` carries no reason: the client can act on none, and naming the sick service leaks internal topology. It is logged server-side instead.

**Banking day** means since midnight `Europe/London` — the platform's first stated timezone convention, so define it once somewhere reusable rather than inline. `StubbedTimeService` makes it testable.

`account-holder-service`'s internal read counts holders, not **User**s: a staff-only User has no holder and must never inflate the bank's customer count. All four holder types count.

New module registration is the usual full set — root `<modules>` and `<dependencyManagement>` (a module declared only in dependency management won't build), the dependency and `@Configuration` import in `malai-api`, and the client base-url property in every scanned configuration of every compile-scope consumer plus the shared client-test defaults.

## Acceptance criteria

- [ ] `openapi.yaml` carries the full four-metric response shape, edited before any controller exists, with the authorization note and the Banking-day window documented
- [ ] `exec-service` module exists, registered in the root build and wired into `malai-api`, owning no tables
- [ ] `GET /api/v1/exec/metrics` returns New customers as a real count for the current Banking day, and the other three as `UNAVAILABLE`
- [ ] A holder created just before and just after the `Europe/London` midnight boundary falls on the correct side of the count
- [ ] A staff-only user (no holder) does not appear in the count
- [ ] An unreachable or slow downstream degrades that one metric to `UNAVAILABLE` within its timeout; the other metrics and the response as a whole are unaffected
- [ ] `hasRole('ADMIN')` enforced: admin 200, customer-only 403, no token 401
- [ ] `account-holder-service`'s internal metric read is service-JWT-scoped and stays out of the public contract
- [ ] `malai-account-holder-client` gains the call, with WireMock-backed request-construction and deserialisation tests per the client-module convention
- [ ] Acceptance tests use full-entity database assertions and strict `noExtraProps()` payload assertions per the house rules
- [ ] `mvn install` green
