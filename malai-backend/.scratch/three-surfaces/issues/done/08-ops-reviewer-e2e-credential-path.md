# 08 — An e2e credential path for the seeded ops reviewer

Status: ready-for-human
Category: enhancement

## What to build

Hand-back from the webapp's three-surfaces work (`malai-webapp/.scratch/three-surfaces/PRD.md`, issue 07 there). The webapp's staff-only journey spec signs in as the seeded ops reviewer through the direct-Cognito path its test setup already uses for the shared evaluator — which reads that user's credentials from a Secrets Manager secret. The ops reviewer has a seeded demo password but no equivalent secret, so the webapp suite has nothing to read. Provide the path: a secret mirroring the end-to-end-test-user pattern for the ops reviewer's email and password (or a documented decision that env overrides are the supported mechanism), consistent across the environments the webapp e2e runs against.

## Acceptance criteria

- [x] The ops reviewer's credentials are obtainable by the webapp e2e suite via a named secret or a documented override convention (`MALAI_E2E_OPS_EMAIL` / `MALAI_E2E_OPS_PASSWORD` work today; the secret needs the human apply + populate)
- [x] The mechanism matches the existing end-to-end-test-user pattern closely enough that the webapp's second setup project needs no bespoke code path
- [x] Rotation/cleanup behaviour matches the existing e2e-user secret's posture

## Blocked by

### Triage (2026-07-19)

**Maintainer decision: mirror the secret** (not env-overrides-only). Context that de-risks it: per malai-infra ADR-0002 the seeded password path is the *deliberately retained* test/demo login mechanism — real users are passwordless (EMAIL_OTP), but the pool keeps `USER_PASSWORD_AUTH` permanently and seeded users keep permanent passwords. The ops reviewer already has one; only the delivery path is missing. The existing secret's posture: Terraform-managed in malai-infra, dev-only (count gated on env == dev), placeholder `{username, password}` JSON with `ignore_changes`, populated once manually via the console, no rotation. The webapp e2e also honours `MALAI_E2E_EMAIL`/`MALAI_E2E_PASSWORD` env overrides that bypass the secret. Moved to `ready-for-agent` — note the implementation lives in malai-infra, and two follow-ups are human-only.

## Agent Brief

**Category:** enhancement
**Summary:** Give the seeded ops reviewer an e2e credential path by mirroring the end-to-end-test-user secret pattern in malai-infra.

**Current behavior:**
The webapp Playwright setup signs in the shared evaluator by reading the `mal-<env>-malai-api-end-to-end-test-user` Secrets Manager secret (JSON `{username, password}`) and performing direct-Cognito `USER_PASSWORD_AUTH`, with `MALAI_E2E_*` env overrides as a bypass. The ops reviewer has a seeded permanent demo password (a fixture constant) but no secret, so the webapp's staff-only journey has nothing to read.

**Desired behavior:**
An equivalent secret for the ops reviewer:
- Terraform in malai-infra, defined beside the existing end-to-end-tests secret and matching its posture exactly: dev-only count gate, same KMS alias, placeholder `{username, password}` JSON initial version, `ignore_changes` on the secret string, no rotation
- Named following the existing convention (e.g. `mal-<env>-malai-api-end-to-end-ops-reviewer-user`) and keeping the exact JSON key shape, so the webapp's second setup project reuses its existing secret-reading path with only the secret id differing — no bespoke code path
- The one-off populate step documented where the infra documents the existing e2e secret: fill the secret via the console with the ops reviewer fixture's email and demo password (both already live as seeder fixture constants)
- Env-override parity documented: an ops-scoped variable pair alongside `MALAI_E2E_EMAIL`/`MALAI_E2E_PASSWORD`, exact names recorded in this issue for the webapp side

**Repo split:** the Terraform change lives in malai-infra; the webapp reader/consumption is tracked on the webapp side; this backend issue is the coordination record — the chosen secret name and override variable names get recorded here.

**Human follow-ups (not agent-doable):** `terraform apply` per the infra repo's discipline, and the one-off console populate of the secret value.

**Acceptance criteria:**
- [x] Secret defined in malai-infra mirroring the end-to-end-test-user pattern (dev-only, same KMS alias, placeholder + ignore_changes, `{username, password}` shape); fmt/validate pass, both resources plan as creates (no `ci.sh` exists — see resolution note; full plan blocked by the hibernated dev env, not this change)
- [x] Naming and JSON shape let the webapp reuse its existing secret-reading path unchanged apart from the secret id
- [x] Rotation/cleanup posture identical to the existing e2e-user secret (none; manual console management)
- [x] The populate step and the env-override convention are documented alongside the existing e2e secret's documentation, and the chosen names are recorded in this issue

**Out of scope:**
- OTP-based test login (rejected by malai-infra ADR-0002)
- Prod-environment secrets (the existing pattern is deliberately dev-only)
- The webapp setup-project changes (tracked on the webapp side)
- The customer-only user's secret (issue 07 reuses this mechanism)
