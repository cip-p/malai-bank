# 06 — Specify what customer endpoints return for a staff-only token

Status: ready-for-human
Category: bug

## What to build

Hand-back from the webapp's three-surfaces work (`malai-webapp/.scratch/three-surfaces/PRD.md`). The seeded ops reviewer holds only `admin` and deliberately owns no customer estate. ### Resolution (2026-07-19)

Implemented per the maintainer decision:

- `MalaiUserWithAccountHolderIdArgumentResolver` (new, in `malai-commons/malai-security`) owns `MalaiUserWithAccountHolderId` controller parameters. When the authenticated principal carries no account-holder context it throws `ForbiddenException(GENERIC_FORBIDDEN)` → 403 with `message: "4999"`, replacing the old 500 GENERIC_ERROR. Registered via `MalaiSecurityWebMvcConfigurer` (`@Order(0)` so it wins over Spring Security's generic `AuthenticationPrincipalArgumentResolver`, which resolved the type mismatch to null and surfaced as 500). Central — no per-controller changes.
- Pinned by tests: `SecurityTest.forbid request when account holder id header is missing in request` (flipped 500/9999 → 403/4999); `AccountsControllerTest.getAccountsReturns403WhenTokenCarriesNoAccountHolderContext` (admin-only token → 403/4999); `AccountHolderControllerTest.getAllAccountHoldersReturnsEmptyListForTokenWithoutCustomerRoleOrEstate` (admin-only token → 200 empty list); `PayeesControllerTest.getReturns403WhenTokenCarriesNoAccountHolderContext` (admin-only token, no holder header → 403/4999 — payees injects `MalaiUserWithAccountHolderId`, so the resolver denies before the role gate) and `PayeesControllerTest.getReturns403WhenTokenHasNoCustomerRole` (holder header present, admin-only token → role-gate 403/9999, previously unpinned). Note: the `hasRole('CUSTOMER')` role gate only answers once holder context exists; with `@EnableMethodSecurity`, argument resolution runs before the method-security interceptor, so a context-less token gets the resolver's 403/4999 on every holder-scoped endpoint regardless of role gates.
- Contract: authorization note in the `openapi.yaml` info description, the rule on the shared `MalAccountHolderIdHeader` parameter (referenced by every holder-scoped operation), and the 200-empty exception documented on `GET /api/v1/account-holder/all`. oasdiff vs main: clean (description-only).

The webapp Access-page assumption check remains tracked on the webapp side.

## Agent Brief

**Category:** bug
**Summary:** A token with no account-holder context gets a specified 403 from holder-scoped endpoints instead of today's 500.

**Current behavior:**
An authenticated staff-only token (Cognito `admin` group, no `customer` group, no `MAL-Account-Holder-Id` header, no estate — the seeded ops reviewer's shape) hits three different outcomes:
- Endpoints gated `hasRole('CUSTOMER')` only (e.g. payees): 403 — the role gate denies before principal resolution. Fine.
- The user-scoped listing `GET /api/v1/account-holder/all` (injects `MalaiUserForUserIdOnly`): 200 with an empty list. Fine.
- Holder-scoped reads gated `hasAnyRole('CUSTOMER','SUPPORT_AGENT','ADMIN')` that inject `MalaiUserWithAccountHolderId` (the accounts family, most account-holder reads): the role gate passes, principal injection then fails on the missing holder context, and the request dies as 500 GENERIC_ERROR (9999). A security test pins this 500 as expected behaviour.

**Desired behavior:**
Whenever an endpoint requires `MalaiUserWithAccountHolderId` and the authenticated request carries no account-holder context, the response is a clean 403 with the standard Forbidden error body — handled centrally in the security/exception-handling layer, not per-controller. The `hasRole('CUSTOMER')` 403s and the `/account-holder/all` 200-empty are unchanged and become documented, pinned behaviour. The contract's authorization notes state the rule for the holder-scoped endpoint family (the admin endpoints already document their `admin`-group requirement and reference a shared Forbidden response — mirror that treatment).

**Key interfaces:**
- The path from `JwtDecoderFilter` (which builds `MalaiUserForUserIdOnly` when the holder header is absent) through `@AuthenticationPrincipal` resolution of `MalaiUserWithAccountHolderId` — where the mismatch currently becomes a 500
- The shared HTTP exception handler, which already maps Spring's access-denied exceptions to 403
- The existing security test pinning the missing-header case as 500 — its expectation flips to 403
- `openapi.yaml`: the shared `Forbidden` response component and the holder-scoped endpoints' documentation

**Acceptance criteria:**
- [x] An admin-only token (no `customer` group, no `MAL-Account-Holder-Id`) calling a representative holder-scoped read (e.g. `GET /api/v1/accounts`) receives 403, pinned by an acceptance test
- [x] The same token calling `GET /api/v1/account-holder/all` receives 200 with an empty list, pinned by an acceptance test
- [x] No holder-scoped endpoint returns 500 for the missing-holder-context case; the security test that pinned 500 now asserts 403
- [x] The contract states the behaviour for the holder-scoped family in its authorization notes; oasdiff against main passes
- [x] `mvn install` green

**Out of scope:**
- Validating that a *supplied* `MAL-Account-Holder-Id` belongs to the JWT user (separate ownership concern; services already enforce via holder-scoped lookups)
- Changing which roles may call customer endpoints
- The webapp Access-page assumption (tracked on the webapp side)
