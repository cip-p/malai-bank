### Triage (2026-07-19)

Two findings that shape the work:
- The seeder assigns Cognito groups explicitly through its own Cognito admin wrapper and never runs the registration path, so the `malai.auth.registration.demo-all-roles` policy cannot leak `admin` onto a seeded user. Exclusion from the demo grant is structural — the new fixture simply never calls the admin group-add.
- Real users are passwordless (EMAIL_OTP), but per malai-infra ADR-0002 ("retain seeded password path for test users; no OTP tap") seeded test users deliberately keep permanent email/password Cognito accounts, and the pool retains `USER_PASSWORD_AUTH`. The new user must be created via the seeder's direct Cognito admin calls with a permanent demo password — not via app registration, which is both all-hats and passwordless (an app-registered user would be unusable by Playwright). Do not attempt an OTP login path for this user.

Maintainer decision on the credential mechanism (shared with issue 08): mirror the `end-to-end-test-user` secret pattern. Moved to `ready-for-agent`.

## Agent Brief

**Category:** enhancement
**Summary:** Seed an idempotent customer-group-only demo identity with a minimal estate, surgical clean, an exact-membership test, and an e2e-reachable credential path.

**Current behavior:**
Only two seeded identities exist: Sarah Mitchell (`customer` + `admin`, full estate) and the ops reviewer (`admin` only, no estate). The registration demo policy grants every hat to app-registered users, so no customer-only user can exist, and the webapp cannot prove the real-bank surface-gating configuration.

**Desired behavior:**
A third seeded identity that holds exactly the `customer` Cognito group, following the established conventions:
- A seed fixture object in the style of the Sarah and ops-reviewer fixtures: pinned deterministic ids, an email alias on the demo mailbox (the ops reviewer uses a `+ops` alias — follow suit, e.g. a `+customer` alias), and a dev-only permanent demo password constant with the same posture as the existing ones
- Cognito side: idempotent create-or-fetch, permanent password via the admin set-password call, a `customer` group add and no other group add; all calls skipped cleanly when Cognito is disabled (blank user-pool id), like the existing seeds
- Estate: users row, individual account holder, address, and account(s) via the same helpers the Sarah seed uses — minimal is fine; full transaction history only if it falls out naturally from reusing existing helpers
- Clean: removes the identity and its estate surgically, keyed by the fixture email like the existing email-scoped delete pattern; append-only chains and system rows untouched; Cognito delete tolerant of an absent user
- Credential path: the same mechanism issue 08 establishes for the ops reviewer — a dev-only Secrets Manager secret following the `end-to-end-test-user` naming and `{username, password}` shape (Terraform in malai-infra), with the existing env-override convention as the bypass — so the webapp Playwright suite signs in via direct-Cognito password auth with no bespoke code path

**Key interfaces:**
- The seed fixture pattern (`SarahMitchellSeed` / `OpsReviewerSeed` style: pinned ids, `EMAIL`, `DEMO_PASSWORD`)
- `SeedCommand` — Cognito seeding and estate build; `CleanCommand` — email-scoped surgical deletes
- The seeder's Cognito admin wrapper (idempotent create-or-fetch, skip-when-disabled)
- The seeder integration test that verifies group adds against the mocked Cognito boundary
