# Standing-order and direct-debit executions run through the real payments machinery

Status: accepted

Standing-order occurrences and direct-debit collections could have been posted straight to the ledger the way the seeders backdate history — synchronous, cheap, and invisible to the payments stack. We decided instead that every execution is a real payment: a standing-order occurrence is an outbound payment initiated through payments-service (FPS with hold → SQS → stub scheme → async settlement; BOOK_TRANSFER when on-us), and a direct-debit collection arrives as an inbound payment on a new `BACS_DIRECT_DEBIT` rail, originated by `malai-stub` so the message genuinely enters through gateway → SQS → consumer. Malai's whole value is that a bank technologist who lifts the lid finds an architecture they would run; a fork between "real payments" and "pretend payments" is exactly the seam that audience would spot, and it would leave the scheduled-execution feature with no messages for message-level tests to assert.

The clock stays bank-side: each owning service runs a per-minute ShedLock'd scheduler that fires a due row **once** and then resyncs `next_*_at` to the next occurrence strictly in the future — no catch-up bursts after downtime. For direct debits this is a deliberate fidelity compromise: in the real Bacs world the creditor decides when to collect, but teaching the stub per-customer mandate state (plus an AUDDIS-style lodgement flow) buys nothing visible in a demo. The stub remains the *apparent* originator of collections while the mandate table remains the source of schedule truth.

Exactly-once execution rests on deterministic per-occurrence end-to-end IDs — `f(instrumentId, occurrenceDate)` — colliding with the existing `payments.end_to_end_id` unique key on the outbound path and the SQS message dedup table on the inbound path. Schedulers are therefore at-least-once by design (initiate first, advance second); no new coordination infrastructure exists, and none should be added to "fix" a re-fired occurrence bouncing off the unique key — that bounce is the mechanism.
