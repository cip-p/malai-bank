# Context map

This repo is multi-context. Each `malai-services/<domain>-service/` directory is one bounded context; this map points at the `CONTEXT.md` for each one that's been written down so far.

Files are created lazily — a context that doesn't yet have a `CONTEXT.md` simply hasn't had its terms grilled out yet. Absence is not a bug. See `docs/agents/domain.md`.

## Contexts

| Service | `CONTEXT.md` | Owns |
|---|---|---|
| `payments-service` | [malai-services/payments-service/CONTEXT.md](malai-services/payments-service/CONTEXT.md) | Payment rails (FPS, future BACS/CHAPS/SWIFT/SEPA), suspense accounts, the outbound-message producers and inbound-message consumers that talk to the per-rail **Gateway**s over SQS, payment lifecycle (`PENDING`/`SETTLED`/`RETURNED`). |
| `fps-gateway`, `bacs-gateway`, `swift-gateway`, `card-gateway` | _not yet written_ (term **Gateway** defined in `payments-service`) | Per-rail connectors bundled into `malai-api`. Bridge internal SQS (`command-*` in, `event-*` out) and the external **Scheme**'s HTTP API. Dumb, stateless translators — no settle/return logic, no database. The external system is WireMock in acceptance tests, `malai-stub` in e2e. `card-gateway` deviates on one leg: the card **authorisation** is synchronous HTTP end-to-end (ADR-0005); its async legs (presentment, reversal, refund) follow the `event-*` queue pattern. |
| `malai-stub` (top-level Maven module inside this repo, **not** bundled into `malai-api`) | _not yet written_ | Two roles. **(1) Outside-world impersonator**: exposes the external schemes' HTTP APIs (rail submit/ack, settle/return + inbound callbacks, CoP, Mambu-shaped APIs later) and holds all rail-specific simulation logic. **No longer touches SQS** — the Gateways own that. **(2) Demo-state introspector**: serves the `Sandbox` surface (webapp ADR-0016, backend ADR-0003) via `GET /demo/counterparties`, exposing its `StubFictionalDirectory` rows to `sandbox-service` for the webapp's Counterparties tab. The existing `POST /demo/inbound/{rail}` routes are reused by the inbound simulator. Deployed as a separate ECS service alongside `malai-api`. |
| `sandbox-service` | _not yet written_ (Counterparty defined in `malai-webapp-v1/CONTEXT.md`) | The controllable demo-state surface served at `/api/v1/sandbox/*`. Owns the controllers that expose the stub's fictional **Counterparty** directory (read) and trigger simulated inbound payments against the active **AccountHolder**'s **Accounts** (write). Card additions: trigger a card purchase (card, merchant, amount), force presentment now, trigger a merchant refund. Depends on `malai-stub-client` for outbound calls. Backed by webapp ADR-0016 and backend ADR-0003. |
| `ledger-service` | [malai-services/ledger-service/CONTEXT.md](malai-services/ledger-service/CONTEXT.md) | The book of record — `transactions`, `ledger_entries`, balance projections, and the bank's internal/system accounts (suspense, scheme-settlement). Designed as a swappable book-of-record (Mambu seam). References accounts by opaque ID only. |
| `account-service` | _not yet written_ | Accounts, the bank's account directory, account identifiers (sort code / IBAN), Confirmation of Payee. The **ledger** that money sits in has moved to `ledger-service`; `account-service` now references it by ID. |
| `account-holder-service` | _not yet written_ | Account holders (Individual / Joint / Business / Sole-Trader), individuals, addresses. |
| `auth-service` | [malai-services/auth-service/CONTEXT.md](malai-services/auth-service/CONTEXT.md) | Cognito-backed passwordless user identity: register / login / verify-code (email one-time codes, no passwords), refresh, sign-out. |
| `payee-service` | _not yet written_ | Holder-scoped saved-counterparty directory. |
| `insights-service` | [malai-services/insights-service/CONTEXT.md](malai-services/insights-service/CONTEXT.md) | Spending-analytics read model over the ledger: the **Category** taxonomy, categorisation of ledger entries, user **Override**s, spending breakdown. Holds no money state; the ledger stays uninterpreted. |
| `direct-debit-service` | [malai-services/direct-debit-service/CONTEXT.md](malai-services/direct-debit-service/CONTEXT.md) | Direct-debit mandates: creditor-originated, customer-cancellable. |
| `standing-order-service` | [malai-services/standing-order-service/CONTEXT.md](malai-services/standing-order-service/CONTEXT.md) | Standing-order schedules: customer-originated recurring push payments. |
| `card-service` | [malai-services/card-service/CONTEXT.md](malai-services/card-service/CONTEXT.md) | Payment cards (debit + credit): the **Card** entity and lifecycle, issuer-side **Card authorisation** processing (approve/decline, capture, reversal) driving ledger Holds/Postings directly, and credit-card product mechanics (credit limit, statement). Card spending does not flow through `payments-service`. |
| `exec-service` | [malai-services/exec-service/CONTEXT.md](malai-services/exec-service/CONTEXT.md) | The bank's headline **Metric**s for the Exec surface, composed over the contexts that own the underlying facts (ADR-0011). Owns no tables and no money state — only the language: **Banking day**, **New customers**, **Deposits**, **Cards issued**, **Payments stopped**, **Metric currency**, and **Unavailable**. |
| `mdr-service` | [malai-services/mdr-service/CONTEXT.md](malai-services/mdr-service/CONTEXT.md) | The **Model Decision Record** — append-only, tamper-evident record of AI-assisted decisions (**Model Decision**) and human rulings on them (**Human Disposition**). Second tenant of the platform hash chain, scope `mdr` (ADR-0007). Provider-agnostic; no LLM dependency. |
| `copilot-service` | [malai-services/copilot-service/CONTEXT.md](malai-services/copilot-service/CONTEXT.md) | The **Copilot** — a read-only investigation aid that assembles a **Timeline** of records for a **Subject** and returns a cited **Explanation**. Owns no tables and no money state; composed over the contexts that own the facts, like `exec-service` (ADR-0011). The MDR's second **Decision point**, and its first **Advisory** one. |
| `aml-service` | [malai-services/aml-service/CONTEXT.md](malai-services/aml-service/CONTEXT.md) | Post-event transaction monitoring and investigation: the **Sweep** over settled payments, **Alert**s recorded as non-advisory **Model Decision**s, the per-account **Case** workflow (`aml_cases`), and the **SAR draft** whose acceptance closes a Case through the **Gate** (ADR-0014). The **Tipping-off** invariant keeps every customer surface blind to all of it. |

## Cross-context terms

These are concepts shared across contexts. Where they're defined, the canonical definition lives in the listed context; other contexts that mention the term should reference back rather than re-defining.

- **Account**, **Bank directory** → `account-service`.
- **Ledger**, **Ledger account**, **Ledger entry**, **Transaction** (ledger grouping) → `ledger-service`.
- **AccountHolder**, **Individual**, **Joint**, **Business**, **Sole-Trader** → `account-holder-service`.
- **User**, **Confirmation code**, **Verification**, **Generated details** → `auth-service` (UI-side framing of the same terms in `malai-webapp-v1/CONTEXT.md`).
- **Payee** → `payee-service`. Distinct from a payment destination — a payee is a *saved* counterparty; a payment can target any sort-code+account-number whether saved as a payee or not.
- **Counterparty** → bank-directory concept (canonically defined for the webapp in `malai-webapp-v1/CONTEXT.md`). In backend terms, a Counterparty is any (sort-code, account-number, name) triple the bank could transact with; a **Payee** is a *saved* Counterparty. The fictional bank directory exposed by `malai-stub` (consumed by CoP and the **Sandbox** surface) is the v1 source of canonical Counterparty data outside malai.
- **Payment**, **Rail**, **Scheme**, **Gateway**, **Suspense account**, **Settlement**, **Return**, **Book transfer** → `payments-service`.
- **Category**, **Override** → `insights-service`. A Category is an interpretation of a **Ledger entry**; the ledger never stores it.
- **Card**, **Card authorisation**, **Credit limit** → `card-service`. A card purchase is a **Card authorisation**, never a **Payment**.
- **Transfer** (UX term, distinct from **Payment**) → see `malai-webapp-v1/CONTEXT.md`. Backend code should prefer **Payment** when speaking about a single instance of money moving via a rail; "Transfer" survives in the existing `TransfersController` URL but is being replaced.
- **Copilot**, **Explanation**, **Claim**, **Source record**, **Timeline**, **Grounding**, **Subject** → `copilot-service`. An Explanation is **Non-authoritative** everywhere: no context may consume one as input to an action.
- **Model Decision**, **Human Disposition**, **Verdict**, **Gate**, **Actionable output**, **Decision point**, **Advisory** → `mdr-service`.
- **Banking day**, **Metric**, **Unavailable** (metric) → `exec-service`. The Banking day (`Europe/London`) is the platform's first stated timezone convention; any later day-scoped figure should adopt it rather than invent a second one.
- **Hash chain**, **Chain scope** → shared infrastructure in `malai-commons/malai-security` (not a bounded context; no CONTEXT.md). One `chain_head` table, one scope per chain: `global` for `audit_events`, `mdr` for the **Model Decision Record** (ADR-0007). The **Ledger** is *not* hash-chained — its integrity is double-entry sum-to-zero.
- **Audit event** → the same shared infrastructure. `AuditWriter` appends, `AuditChainVerifier` replays, `AuditReader` answers "what happened to this resource" by `(resourceType, resourceId)` in chain order. Every service writes directly, so every service reads directly too — no context owns `audit_events`, and a reader that lived in one would make it the de facto owner.
- **Alert**, **Case**, **Typology**, **Evidence set**, **Sweep**, **SAR draft**, **Tipping-off** → `aml-service`. An Alert is a **Model Decision**, never a table row here; ruling on one is a **Human Disposition** through the MDR door, and a Case's terminal transitions are **Gate**-governed (ADR-0014).
