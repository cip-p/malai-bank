# Move money: transfers, payees, and read-only direct debits + standing orders

Status: ready-for-agent

## Problem Statement

The webapp now ships the full auth surface and the Accounts surface, but a bank decision-maker watching the demo runs out of bank-fluency to evaluate the moment they want to _do_ something with their money. They can see their balance and their **Transactions**, but they cannot make a one-off **Transfer**, save a **Payee** they pay regularly, or inspect the **Direct Debits** and **Standing Orders** flowing through their **Accounts** — the four primitives that define a UK retail bank. The platform behind the webapp already implements all four in the OpenAPI (`Transfers`, `Payees`, `DirectDebits`, `StandingOrders` sections); only the UI surface to demonstrate them is missing.

That gap matters for the demo's core value: a prospect concludes "this looks like a real bank" only after they have seen the bank do the bank-shaped things. A surface that stops at "here's the balance" understates the platform.

## Solution

A new **Move money** section, plus two additions to the existing **AccountDetailPage**.

- **`/move/*`** — single top-nav slot whose `/move` root redirects to `/move/send`. Every sub-page renders a persistent **Move-money sub-nav** with four items: _Send money_ · _Payees_ · _Direct Debits_ · _Standing Orders_.
- **`/move/send`** — the one-off **Transfer** form. Source-account dropdown above three destination tabs: **My accounts** (own-to-own across the **Active AccountHolder**'s **Accounts**), **Saved payee** (select from `/api/v1/payees`), **New payee** (manual entry with **Confirmation of Payee** before submit, optional save-as-payee). The form is two-step: enter details → confirm verdict + send.
- **`/move/payees`** — list of saved **Payees**, sorted alphabetically by `nickname ?? name`. Each row offers a delete affordance whose confirm modal cross-checks the loaded **Standing Order** list and warns when any SO references the payee. An "Add payee" button routes to `/move/payees/new`.
- **`/move/payees/new`** — create form for a new **Payee**: name + sort code + account number + optional nickname. Confirmation of Payee runs on submit; `CLOSE_MATCH` offers the on-record name as a one-click substitution that updates the _saved_ payee's name (not just a transient display); `NO_MATCH` warns but allows proceed.
- **`/move/direct-debits`** — read-only list of `DirectDebitResponse`. Variable-amount DDs render the literal word **"Variable"**, never `£0.00`. Sorted by `nextCollectionAt` asc, with null-bucket-to-bottom alphabetised by `creditorName`.
- **`/move/standing-orders`** — read-only list of `StandingOrderResponse`. When `payeeId` is non-null _and_ resolves in the loaded payees list, `payeeName` renders as a link to `/move/payees#${payeeId}` that scrolls the Payees list to the matching row; otherwise plain text.
- **`AccountDetailPage`** — gains a primary **Send money** CTA linking to `/move/send?from=<accountUid>` (which pre-fills the source-account dropdown) and a **Scheduled payments on this account** section showing two distinct sub-lists (DDs / SOs) filtered client-side by `accountId`, each with a "View all" link to its hub.
- **`AppShell.PrimaryNav`** — gains a single `Move money` link alongside the existing `Accounts`.

The slice keeps three deliberately uncomfortable constraints: **Direct Debits and Standing Orders are read-only** because the OpenAPI contract only exposes `GET` for them (writing UI ahead of contract would lead the workspace OpenAPI-first rule); **Payees have no Edit affordance** because the OpenAPI exposes no `PUT`/`PATCH` (see [ADR-0009](../../docs/adr/0009-payees-no-edit-no-fake-patch.md)); and **error mapping follows ADR-0007 anti-enumeration** with one new carve-out — an inline form-level error for **insufficient-funds** `409` on transfer, justified and bounded by [ADR-0008](../../docs/adr/0008-insufficient-funds-inline-error-carve-out.md).

After this PRD lands, the four "real-bank" primitives — making a payment, saving a counterparty, watching recurring activity — all have a UI home, and the demo can run end-to-end through them.

## User Stories

1. As a signed-in **User**, I want a single `Move money` link in the primary nav, so that the section is discoverable from anywhere in the app without inflating the tab bar.
2. As a signed-in **User**, I want to land on the Send-money screen by default when I click `Move money`, so that the most common action is one click away.
3. As a signed-in **User**, I want a persistent Move-money sub-nav across all four sub-pages, so that I can move between _Send money_ / _Payees_ / _Direct Debits_ / _Standing Orders_ without going back to a hub.
4. As a signed-in **User** on the **Active AccountHolder**'s **AccountDetailPage**, I want a primary "Send money" CTA that pre-fills the source account on the transfer form, so that I do not have to re-pick the account I just came from.
5. As a signed-in **User** on **AccountDetailPage**, I want a "Scheduled payments on this account" section showing **Direct Debits** and **Standing Orders** that affect this account in two distinct sub-lists, so that I can scan the recurring activity for this account in context without losing the product distinction between DD and SO.
6. As a signed-in **User** on **AccountDetailPage**, I want each scheduled-payments sub-list to show a "View all" link to its hub screen, so that I can see the holder-wide list without losing my place.
7. As a signed-in **User** on `/move/send`, I want a source-account dropdown above the destination tabs, so that the _source_ is one decision and the _destination mode_ is the next decision.
8. As a signed-in **User** arriving from `/move/send?from=<accountUid>`, I want that account already selected as the source, so that the per-account context carries through.
9. As a signed-in **User** with multiple reachable **Accounts**, I want a **My accounts** destination tab listing all of my other accounts, so that I can move money between my own accounts (the canonical Sarah-Mitchell demo for CURRENT→SAVINGS).
10. As a signed-in **User** with only one reachable **Account**, I want the **My accounts** tab still visible (not hidden) with an empty-state message "_You only have one account — nothing to send to yourself_", so that the IA looks identical across demo personas.
11. As a signed-in **User** on the **Saved payee** tab, I want to see my saved **Payees** as a selectable list with amount and reference fields visible below, so that I can pick a payee and enter the amount without an intermediate step.
12. As a signed-in **User** on the **New payee** tab, I want to enter name, sort code, account number, amount, and reference in one screen, with an optional "Save as a payee" checkbox so that I can persist this counterparty for next time.
13. As a signed-in **User** entering a sort code, I want the dashes auto-inserted as I type (`123456` → `12-34-56`), so that I do not have to manage punctuation, and so that paste-from-bank-statement works regardless of dash inclusion.
14. As a signed-in **User** entering an account number, I want non-digits stripped on input and the field limited to 8 digits, so that paste-from-bank-statement with embedded spaces does the right thing.
15. As a signed-in **User** entering an amount, I want a `£` adornment on the left of the input (not a placeholder), `inputMode="decimal"`, normalisation to two decimals on blur, and rejection of more-than-two decimals / scientific notation / negatives / values below `£0.01` / values above `£999,999.99`, so that the amount I'm about to send is unambiguous.
16. As a signed-in **User** entering a reference, I want a single-line input labelled _Reference (optional)_ with a character counter that appears only when I've used more than 400 of the 500 allowed characters, so that I don't see permanent counter clutter for short references.
17. As a signed-in **User** on the **New payee** tab, I want the destination name field labelled _Name on the account_ rather than _Payee name_, so that the framing is the counterparty's banking identity rather than my local label for them.
18. As a signed-in **User** pressing Continue on **New payee**, I want **Confirmation of Payee** to run _before_ the transfer is submitted, with the verdict driving the next screen, so that I am never sent money to an account whose name we did not verify against record.
19. As a signed-in **User** receiving a `MATCH` verdict, I want to advance silently to the confirmation summary, so that the COPA result is invisible when there's nothing to flag.
20. As a signed-in **User** receiving a `CLOSE_MATCH` verdict, I want to see _"On record as {onRecordName} — you entered {enteredName}"_ with two buttons: _Use the on-record name_ and _Keep what I typed and continue_, so that I can correct a near-miss without retyping.
21. As a signed-in **User** clicking _Use the on-record name_ with **Save as a payee** ticked, I want the saved Payee record stored with the on-record name (not what I originally typed), so that the next send to this Payee returns `MATCH`.
22. As a signed-in **User** receiving a `NO_MATCH` verdict, I want a warning _"We couldn't verify this account. Please double-check the details."_ with two buttons: _Edit details_ and _Send anyway_, so that I retain override authority per UK COPA convention but am clearly informed.
23. As a signed-in **User** on the **Saved payee** or **My accounts** tab, I want **no COPA call**, so that the form does not waste time re-verifying a destination that was either previously verified (saved payee) or is my own account.
24. As a signed-in **User** pressing Continue on any tab, I want a confirmation step rendering the transfer summary as plain text (not editable fields), so that the verification screen is unambiguously different from the entry screen.
25. As a signed-in **User** on the confirmation step, I want a Back button that returns me to the entry form with all my values preserved, so that I can correct a mistake without re-typing.
26. As a signed-in **User** pressing Send on the confirmation step, I want the transfer submitted with an `Idempotency-Key` generated per submit attempt and the Send button disabled while the mutation is pending, so that a double-click cannot duplicate the transfer.
27. As a signed-in **User** whose transfer succeeded, I want a success toast, the source account's transaction list and balance invalidated in the query cache, and the form reset, so that returning to `/accounts/<source>` shows the new state.
28. As a signed-in **User** whose transfer failed due to **insufficient funds** (`409` with the insufficient-funds `MalaiCode`), I want an inline form-level error _"Not enough money in this account."_ — _not_ a toast — and the form to stay interactive so I can edit the amount and retry, per [ADR-0008](../../docs/adr/0008-insufficient-funds-inline-error-carve-out.md).
29. As a signed-in **User** whose transfer failed for any other 4xx reason, I want a generic toast _"Something went wrong. Please try again."_ per [ADR-0007](../../docs/adr/0007-anti-enumeration-error-policy.md), so that the platform never leaks which input or which state was the problem.
30. As a signed-in **User** on `/move/payees`, I want a list of my saved **Payees** sorted alphabetically by `nickname ?? name`, with name, nickname (if present), and partial sort-code/account-number on each row, so that I can scan a long list predictably.
31. As a signed-in **User** with no saved **Payees**, I want an empty state _"No saved payees yet — save someone you pay regularly so you don't have to re-enter their details next time."_ with an _Add payee_ CTA, so that the screen teaches the concept on first visit.
32. As a signed-in **User** clicking _Add payee_, I want a dedicated `/move/payees/new` route (not a modal), so that the URL is shareable and the form survives an accidental browser-back without disappearing.
33. As a signed-in **User** submitting the **Add payee** form, I want **Confirmation of Payee** to run before the create POST, with the same three-verdict UX as the transfer form (silent MATCH, name-swap CLOSE_MATCH, warn-and-proceed NO_MATCH), so that a saved Payee always carries the verified name where possible.
34. As a signed-in **User** with a saved **Payee** I want to remove, I want a delete affordance on the row, opening a confirm modal _"Remove {payeeName}? You can add them again later."_, so that the destructive action is acknowledged.
35. As a signed-in **User** about to delete a **Payee** that one or more **Standing Orders** reference, I want the confirm modal upgraded to _"Remove {payeeName}? {n} standing order(s) reference this payee — they'll continue running but lose their saved-payee link."_, so that I am informed of the side effect before I commit.
36. As a signed-in **User** whose delete returned `404`, I want the row to disappear and the success path to run, so that an already-deleted payee does not error noisily.
37. As a signed-in **User** of `/move/direct-debits`, I want a flat list of my active **Direct Debits** sorted by `nextCollectionAt` ascending, with `creditorName` as the primary label, `reference` as a small secondary line, amount on the right, frequency label, and a "Next: " caption, so that I can see what's coming up.
38. As a signed-in **User** viewing a variable-amount **Direct Debit** (a utility-style DD with `null` `amountMinorUnits`), I want the row to show the literal word _"Variable"_ in muted weight, never `£0.00`, so that the amount field is honest.
39. As a signed-in **User** viewing a **Direct Debit** with `null` `nextCollectionAt`, I want the row to show _"Next: not scheduled"_ in the next-date caption, so that absence is named.
40. As a signed-in **User** with no active **Direct Debits**, I want an explanatory empty state — _"No active direct debits. A direct debit is a recurring pull of money initiated by the company being paid — set up via the company, not the bank."_ — with **no** "Create" CTA, so that the screen honestly reflects what the platform exposes.
41. As a signed-in **User** of `/move/standing-orders`, I want a flat list of my active **Standing Orders** sorted by `nextPaymentAt` ascending, with the same row shape as the DD list (counterparty, reference, amount, frequency, next-date), so that the two read-only screens read consistently.
42. As a signed-in **User** viewing a **Standing Order** whose `payeeId` resolves to a saved **Payee**, I want `payeeName` rendered as a link to `/move/payees#${payeeId}` that scrolls the Payees list to the matching row, so that I can jump between an SO and its linked saved counterparty.
43. As a signed-in **User** viewing a **Standing Order** whose `payeeId` is `null` or does not resolve, I want `payeeName` rendered as plain text, so that I never see a broken link.
44. As a signed-in **User** with no active **Standing Orders**, I want an explanatory empty state — _"No active standing orders. A standing order is a recurring payment you set up from your account on a fixed schedule."_ — with no "Create" CTA, so that the screen matches the DD-empty discipline.
45. As a signed-in **User** with multiple reachable **Accounts**, I want each row in both DD and SO lists to show a small account chip (e.g. _CURRENT_) so I can tell which account the recurring activity hits; with a single Account I want the chip hidden so it doesn't add noise.
46. As a signed-in **User** with dates in the current year, I want next-date captions formatted as _"Next: 23 May"_; for dates within seven days, _"Next: in 3 days"_; for dates in other years, _"Next: 23 May 2025"_, so that the display adapts to recency.
47. As a signed-in **User** while any of these screens is loading, I want a skeleton matching the eventual list shape, so that the surface does not flicker between empty and populated states (consistent with the existing `AccountsPage` / `TransactionsList` pattern).

## Implementation Decisions

**Information architecture.** Hub model under `/move/*`: `MoveMoneyLayout` renders the **Move-money sub-nav** + `<Outlet />`. `/move` redirects to `/move/send`. All four sub-routes (`/move/send`, `/move/payees`, `/move/payees/new`, `/move/direct-debits`, `/move/standing-orders`) live under the layout. Choosing `/move/*` as a URL prefix (rather than four flat top-level routes) gives the sub-nav a clean `pathname.startsWith('/move/')` predicate. The `AppShell.PrimaryNav` gains one new link with `aria-current="page"` when `/move/*` is active.

**Transfer destination model.** Three modes implemented as a segmented control inside `TransferPage`. The source-account dropdown is a single control above the tabs (one source for all three modes). `?from=<accountUid>` query pre-selects the source. **My accounts** lists the **Active AccountHolder**'s other **Accounts** sourced from `useAccounts` filtered to exclude the source. **Saved payee** sources from `usePayees` with the destination fields hidden but populated on select. **New payee** is manual entry plus the optional "Save as a payee" checkbox.

**Confirmation of Payee.** Called only on submit, only on the **New payee** transfer tab and the **Add payee** form. Verdict handling encapsulated in the `copaNextStep` pure helper and the `CopaVerdictPanel` component. `CLOSE_MATCH` with _Use the on-record name_ substitutes both the displayed counterparty name and (when saving) the persisted Payee's `name`. `NO_MATCH` _Send anyway_ / _Save anyway_ proceeds without any data marker — the backend audits separately. Idempotency-Key per COPA check is independent of the subsequent transfer/create POST's key.

**Payee mutation surface.** Per [ADR-0009](../../docs/adr/0009-payees-no-edit-no-fake-patch.md), Create + Delete only — no Edit affordance. The delete flow runs an SO cross-check (`findStandingOrdersByPayee` pure helper) against the already-loaded `useStandingOrders` query and upgrades the confirm-modal copy when matches are found. Delete is optimistic; `204` confirms; `404` is treated as success; other 4xx falls through to the generic toast.

**Direct Debits and Standing Orders lists.** Both screens are read-only with no row interaction (no expand, no detail page). Sort order: `nextCollectionAt` / `nextPaymentAt` asc, nulls bucketed to bottom and alphabetised within the bucket via `sortByNextDate`. Variable DDs (null `amountMinorUnits`) render _"Variable"_. Null next-date renders _"Next: not scheduled"_. SO rows resolve `payeeId` against `usePayees` to decide whether `payeeName` is a link.

**AccountDetailPage additions.** A `SendMoneyCta` button (primary variant) links to `/move/send?from=<accountUid>`. A `ScheduledPaymentsPeek` section renders two distinct sub-lists — Direct Debits and Standing Orders — each filtered client-side by `accountId`, each with a _View all_ link. The peek reuses `DirectDebitRow` / `StandingOrderRow` to stay visually consistent with the hub screens.

**Error mapping.** Per [ADR-0008](../../docs/adr/0008-insufficient-funds-inline-error-carve-out.md): generic toast everywhere, with one carve-out — `409` insufficient-funds on `POST /transfers` is an inline form-level error (_"Not enough money in this account."_) leaving the form interactive. Field-level RHF + generated-Zod validation per [ADR-0004](../../docs/adr/0004-generated-zod-as-form-schema-source.md) is unchanged. The global `401` handler (existing) handles auth expiry.

**Idempotency-Key handling.** `mintIdempotencyKey()` (UUID v4) is called _at submit time_, attached to the mutation input, and discarded when the form resets after success. Pending mutations disable the submit button, so double-clicks are not the failure mode. The rare refresh-during-pending edge case is not protected against in v1; documented in `0008` and reasoned through there.

**Domain language committed.** New `CONTEXT.md` entries: **Payee**, **Transfer**, **Direct Debit**, **Standing Order**, **Move money**. **"Payments"** is explicitly avoided as a nav label or umbrella term (collision with DDs and card payments, flagged from the prior auth-tracer glossary work). The split between code-term (_Transfer_) and user-facing copy (_Send money_) mirrors the existing **Registration** / "Sign up" split.

**Modules sketched.** Pure utilities in `src/lib/`: `parseAmount`, `formatSortCodeInput`, `formatNextDate`, `sortByNextDate`, `mintIdempotencyKey`, `copaNextStep`. Hooks following the existing `useAccounts` pattern, located by domain (`src/payees/`, `src/move/transfer/`, `src/direct-debits/`, `src/standing-orders/`): `usePayees`, `useCreatePayee`, `useDeletePayee`, `useConfirmationOfPayee`, `useTransfer`, `useDirectDebits`, `useStandingOrders`. Deep component: `CopaVerdictPanel`. Shallow components: `MoveMoneySubNav`, `AmountInput`, `SortCodeInput`, `AccountNumberInput`, `PayeeRow`, `DirectDebitRow`, `StandingOrderRow`, `ScheduledPaymentsPeek`, `DeletePayeeDialog`. Pages: `MoveMoneyLayout`, `TransferPage`, `PayeesPage`, `AddPayeePage`, `DirectDebitsPage`, `StandingOrdersPage`. Modifications: `App.tsx` router, `AppShell.PrimaryNav`, `AccountDetailPage`.

## Testing Decisions

**Posture.** Test external behaviour only — never implementation details. A test that asserts the COPA verdict reducer returns the right next-state given the inputs is a behaviour test; a test that asserts an internal callback was called with a specific argument is an implementation test we will not write. Vitest + `@testing-library/react` + `@testing-library/user-event` + jsdom, mirroring `src/test/setup.ts` and the prior-art tests already in the repo.

**Pure utility modules (all six get exhaustive Vitest tests).** `parseAmount` — zero, negative, more-than-two-decimals, scientific notation, leading/trailing whitespace, leading `£`, leading `+`, comma decimal separator, integer pounds, single decimal, two decimals, soft-cap boundary, empty string. `formatSortCodeInput` — empty, partial (`1`, `12`, `123`, `1234`, `12345`, `123456`), pre-dashed input, paste with spaces, deletion that crosses a dash boundary. `formatNextDate` — null, past date in current year, future date in current year, future date within 7 days (relative), future date in prior year, future date in future year. `sortByNextDate` — empty array, all nulls, mixed, ties (alphabetical fallback). `mintIdempotencyKey` — uniqueness across many calls. `copaNextStep` — all three verdicts crossed with both intents (`transfer` / `save-payee`) and the name-substitution branch for `CLOSE_MATCH`. Prior art: `formatCurrency.test.ts`, `formatRelativeDateGroup.test.ts`, `groupTransactionsByDate.test.ts` — same shape and edge-case discipline.

**Hooks (all seven get tests mirroring the existing pattern).** `usePayees` / `useDirectDebits` / `useStandingOrders` — initial loading, success, error, refetch-on-invalidate. `useCreatePayee` / `useDeletePayee` / `useTransfer` / `useConfirmationOfPayee` — happy path, error path, idempotency-key attachment, query-cache invalidation on success. Prior art: `useAccounts.test.tsx`, `useAccount.test.tsx`, `useTransactions.test.tsx`, `useIdentifiers.test.tsx`, `useBalance.test.tsx` — same QueryClient wrapper and fetch-mock strategy.

**Deep component (`CopaVerdictPanel`).** One test per verdict branch — `MATCH` renders the silent path forward; `CLOSE_MATCH` renders the on-record-name swap UI and fires the right callbacks for each button; `NO_MATCH` renders the warn-and-proceed UI and fires the right callbacks. Crossed with both intents (`transfer` / `save-payee`) where the rendered copy differs.

**Page-level integration (covered through Playwright E2E rather than additional Vitest coverage).** The three transfer destination modes, the payee create-with-COPA flow, the payee delete-with-SO-cross-check flow, the DD/SO read-only happy paths, and the per-account peek on `AccountDetailPage`. Auth setup reuses the shared Cognito user pattern from `tests/e2e/auth.setup.ts` — workers=1, fullyParallel=false (the established testing posture in the repo CLAUDE.md). Demo fixtures may need backend seeding for Sarah-Mitchell to have DDs / SOs / Payees populated; flagged below.

**A11y.** `tests/e2e/a11y.spec.ts` extends to cover `/move/send`, `/move/payees`, `/move/payees/new`, `/move/direct-debits`, `/move/standing-orders`, the AccountDetailPage with the new CTA + peek, and the delete-confirmation modal. Per [ADR-0006](../../docs/adr/0006-a11y-baseline.md) the bar is "axe-clean and reasonable focus management"; the confirmation modal needs explicit focus return on dismiss.

## Out of Scope

- **Creating, amending, or cancelling Direct Debits or Standing Orders.** OpenAPI only exposes `GET` for both; lifting this requires backend contract changes first per the workspace OpenAPI-first rule, then a separate PRD on this repo.
- **Editing a saved Payee.** OpenAPI exposes no `PUT`/`PATCH`; deliberate, per [ADR-0009](../../docs/adr/0009-payees-no-edit-no-fake-patch.md). When the backend adds the endpoint the ADR is superseded.
- **Confirmation of Payee on-blur** (decided: on submit only).
- **Confirmation of Payee on the My-accounts or Saved-payee transfer tabs** (decided: only on the New-payee path and the Add-payee form).
- **Per-account-grouped DD/SO views beyond the AccountDetailPage peek.** The hub screens stay flat with account chips.
- **Detail / drill-down screens for individual DDs or SOs.** Read-only rows show everything we have.
- **Idempotency-Key persistence across page refreshes.** Rare edge case; documented in ADR-0008 as a deliberate v1 trade-off.
- **Inline disclosure of the actual remaining balance on insufficient-funds.** Deferred per ADR-0008; the balance is on-screen in the source dropdown.
- **Holder switcher.** Active **AccountHolder** resolution remains _"first INDIVIDUAL"_ (per `CONTEXT.md`) until a demo scenario surfaces a second holder type.
- **Multi-currency / FX.** `Currency` enum is GBP-only in v1.
- **Pay-from-Payee CTA** (a button on a Payee row that opens the transfer form pre-filled with that payee). The demo flow goes via `/move/send` → Saved-payee tab → pick.
- **Two-factor / step-up auth on transfer.** Not in the OpenAPI contract for `/transfers`; out of demo regulatory scope.
- **`/move` index/hub page.** Decided in the grilling session: `/move` redirects to `/move/send`; the sub-nav already exposes the breadth from any sub-page.

## Further Notes

- **New ADRs landed alongside this PRD**: [ADR-0008](../../docs/adr/0008-insufficient-funds-inline-error-carve-out.md) (the insufficient-funds inline-error carve-out from ADR-0007's anti-enumeration policy) and [ADR-0009](../../docs/adr/0009-payees-no-edit-no-fake-patch.md) (no fake-PATCH Edit on Payees until the backend adds the endpoint).
- **`CONTEXT.md` updates landed alongside this PRD**: glossary entries for **Payee**, **Transfer**, **Direct Debit**, **Standing Order**, and **Move money**, plus expansion of the _"payment is overloaded"_ note in the existing **Transaction** entry.
- **Backend fixture coordination.** For a Sarah-Mitchell-style demo to populate the read-only DD and SO screens with anything other than empty states, the backend's demo seed will need DD and SO records against Sarah's accounts plus a few Payees. If those are not present in the seed at build time, the screens will still ship correctly (empty states are part of this PRD) but a demo viewer signing in as Sarah will see "No active direct debits / standing orders / payees" — flag to `malai-backend` before a fixture-dependent demo.
- **OpenAPI snapshot freshness.** The repo's `./openapi.yaml` snapshot must match `malai-backend`'s `static/openapi.yaml` at the time this PRD lands; if the contract has moved, refresh and re-run `npm run openapi:gen` before starting work.
- **No comments anywhere — including tests.** Workspace invariant. Applies to every file this PRD adds or modifies.
- **Existing patterns to mirror**: `src/accounts/` for the domain folder layout and hook shape; `src/lib/formatCurrency.ts` + `formatRelativeDateGroup.ts` for pure-utility-with-tests style; `src/pages/SettingsPage.tsx` and `src/auth/` mutation hooks for RHF + Zod + generated-mutation wiring; `tests/e2e/auth.setup.ts` for the storageState-based auth in Playwright.
