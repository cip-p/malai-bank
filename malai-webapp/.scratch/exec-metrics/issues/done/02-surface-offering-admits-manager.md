# 02 — Surface offering admits a second Role per Surface

Status: ready-for-agent
Category: enhancement

## What to build

`MANAGER` arrives as a narrow **Role** that **Offers** the Exec surface and nothing else (backend ADR-0010). The surface-offering module cannot express that today: its gate map holds exactly one Role per **Surface**, and Exec now has two — `MANAGER` and `ADMIN`.

Reshape the gate map from surface → one Role to surface → set of Roles, and let every consumer of the module — the per-surface guards, the user-menu switcher rows, the **Landing** precedence, and the **Access page** — pick up the change without each re-deriving role logic. This stays presentation: role enforcement lives at the API and does not move.

A `MANAGER`-only session lands on `/exec` (the first Offered Surface in the existing precedence), sees Banking and Ops as **Withheld** with the Access page rather than a redirect or a NotFound, and the user menu offers no Surface it cannot reach. A session holding both `MANAGER` and `ADMIN` — which every demo evaluator does — behaves exactly as it does today.

Refresh the snapshot and regenerate so the `roles` union includes `MANAGER`.

## Acceptance criteria

- [ ] The gate map expresses multiple Roles per Surface; Exec is Offered to both `MANAGER` and `ADMIN`
- [ ] Snapshot refreshed and client regenerated; the generated `roles` union includes `MANAGER`
- [ ] Unit tests cover every role combination, including `MANAGER`-only, `MANAGER`+`ADMIN`, and the unchanged existing cases
- [ ] A `MANAGER`-only session lands on `/exec`
- [ ] A `MANAGER`-only session sees the Access page on Banking and Ops routes — not a redirect, not NotFound
- [ ] The user menu offers only Surfaces the session can actually reach
- [ ] No behaviour change for sessions holding `ADMIN`
