# Sandbox outbound outcome is a property of the destination Counterparty, not an armed scheme state

The **Sandbox** surface (ADR-0016) needs to demonstrate a small set of outbound payment outcomes — happy-path settle, return-with-reason for every `ReturnReason` value, and "stuck in-progress" — against fixed, named **Counterparties** so that a bank-exec demonstrator or unguided prospect can read a table and predict what will happen before they send.

The accepted shape: each row in `malai-stub`'s `StubFictionalDirectory` carries an `outboundOutcome` enum (`SETTLES | RETURNS | STUCK_PENDING`) and, when `RETURNS`, an accompanying `returnReason`. When the stub's FPS or BACS scheme handler receives an outbound submission, it looks up the beneficiary in the directory and the row decides the outcome. There is no per-session "arm the next return" state on the Sandbox path. Destinations _not_ in the directory settle by default.

## Considered options

- **Destination-deterministic on the Counterparty row** _(accepted)_. The table on the **Counterparties** tab can carry a stable `Outcome` column because outcome ≡ destination. An unguided prospect reads the row and acts without any hidden arming step. A live demo narrates "watch what happens when I send to this returning account" — no stage console, no leakage between scenarios, no "did I forget to disarm". The catalogue-first IA from ADR-0016 only works if the Outcome column is meaningful at row-read time, which arming-based state cannot provide.
- **Arm-style, like the existing `POST /demo/arm-return`.** The Sandbox UI would click "Arm next return as `INSUFFICIENT_FUNDS`" and the user would then go run a payment against any destination. Rejected: introduces hidden one-shot session state; an unguided prospect who navigates away and back finds the arm in an unexplained state; the "stuck in-progress" axis from the brief is not naturally an arm-style override; the Outcome column on the Counterparties tab loses meaning because the destination doesn't determine the outcome.
- **Hybrid: destination-deterministic by default, arm-style as a per-payment override.** Preserves the escape hatch ("force a specific outcome on an arbitrary destination"). Rejected for v1: double the API surface; the catalogue already covers every `ReturnReason` and the stuck-in-progress case via fixtures; if a demo eventually demands forcing an outcome on a user-typed destination, this is additive over the deterministic model.

## Consequences

- The **`outboundOutcome` enum** is the canonical Sandbox vocabulary for outcome; the existing `ReturnReason` enum on `payments-service` is preserved unchanged and used as the payload when `outboundOutcome = RETURNS`.
- The existing `POST /demo/arm-return` and `GET /demo/fps/returns` stub routes are **not** wired into the Sandbox path — they remain in place for backwards compatibility with whatever existing tests / scripts consume them, but the new destination-deterministic logic does not consult their state. A future cleanup could remove them; out of scope for the Sandbox slice.
- The **catalogue is static and global** — the row that decides the outcome is the same row every signed-in user sees. No persistence, no per-user state, no migrations. Adding ad-hoc per-user overrides later is additive (see Q6 in the design grilling).
- **`STUCK_PENDING` is genuinely stuck** — no auto-resolution, no timeout. Stuck Transactions accumulate on the user's Account until the existing `demo-reset.sh` flow wipes-and-reseeds. Per-payment manual unstick is a clean v2 addition if a demo demands it.
- **Unknown destinations settle.** A user who types an arbitrary sortcode + account-number into a Transfer reaches a counterparty not in the directory; the stub treats that as `SETTLES`. This preserves the happy-path narrative for "anything reasonable works" and concentrates failure modes on the named fixtures in the catalogue.
- The Counterparties tab on `/sandbox` can therefore render a meaningful `Outcome` column per row — `Settles`, `Returns (INSUFFICIENT_FUNDS)`, `Stays in progress` — which is the single piece of information the catalogue-first IA needs to function.
